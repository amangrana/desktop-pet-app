# 桌面宠物放置游戏：功能设计文档

> 状态：共同设计中  
> 版本：0.16  
> 更新日期：2026-07-19  
> 首发平台：Windows，后续发布至 Steam

## 1. 产品概念

一款常驻 Windows 桌面的轻量宠物放置游戏。宠物既是有生命感的桌面伙伴，也是温和的专注与健康提醒助手。玩家可以观察、点击和装扮宠物，也可以与具有固定性格和长期记忆的宠物对话。

### 一句话描述

一个会陪你工作、提醒你休息，并逐渐记住你的桌面小伙伴。

### 核心体验

1. **陪伴感**：宠物即使没有被操作，也会通过待机和偶发动作表现出生命感。
2. **低打扰**：需要时出现，不需要时安静待在桌面一角。
3. **轻互动**：点击、对话、切换形象和观察动作都不需要复杂操作。
4. **实际帮助**：专注计时、喝水和活动提醒真正融入日常。
5. **逐渐熟悉用户**：对话记忆和长期关系让宠物越来越像“我的宠物”。

## 2. 设计原则

- 宠物不能妨碍正常使用电脑。
- 所有提醒都能关闭、延后或自定义。
- 核心陪伴功能在离线状态下仍可使用。
- AI 对话是增强功能，不能成为宠物运行的必要条件。
- 第一版优先做出“活着的感觉”，再扩展装扮、商店和复杂养成。
- 任何涉及聊天记录和长期记忆的功能，都必须允许用户查看、删除和关闭。

## 3. 目标用户与使用场景

### 目标用户

- 长时间使用 Windows 工作或学习的人。
- 喜欢桌面宠物、电子宠物或轻量放置游戏的人。
- 希望获得温和提醒，但不喜欢传统效率软件压力感的人。
- 想在独自工作时获得轻度陪伴的人。

### 典型使用场景

- 用户开始工作，启动一个 25 分钟专注时段，宠物进入陪伴工作动作。
- 专注结束后，宠物通过动画和气泡提醒用户休息。
- 用户长时间没有活动，宠物提醒站起来走动或喝水。
- 用户工作间隙点击宠物，触发抚摸、躲避、回应或随机动画。
- 用户打开对话框，与宠物聊几句；宠物记得用户之前提过的偏好或近况。

## 5. 功能详细设计

### 5.1 桌面窗口

#### 必需行为

- 宠物显示在透明、无边框窗口中。
- 用户可以拖动宠物到桌面任意位置。
- 关闭并重新打开后，恢复上次的位置。
- 可以开启或关闭“始终置顶”。
- 右键宠物或托盘图标可以打开快捷菜单。
- 快捷菜单至少包含：开始专注、提醒设置、切换宠物、始终置顶、隐藏宠物、退出。

#### 建议行为

- 支持多显示器，并防止宠物恢复到已经断开的显示器之外。
- 可选择“随 Windows 启动”，默认关闭。
- 全屏应用运行时可选择自动隐藏或保持显示。
- 提供宠物显示比例，例如 75%、100%、125% 和 150%。
- 后续可加入“鼠标穿透”模式，避免宠物挡住点击。

#### 初步验收标准

- 始终置顶状态切换后立即生效。
- 宠物位置、大小和置顶设置在重启后保持。
- 宠物不能因为分辨率或显示器变化而永久跑出屏幕。
- CPU 和内存占用要足够低，不影响日常办公。

### 5.2 宠物形象与外观

#### 首版范围

- 至少提供 2 个可切换的宠物形象，开发阶段可以先使用占位素材。
- 每种形象使用相同的动作状态名称，允许共用行为逻辑。
- 切换形象后，位置、提醒设置和关系数据保持不变。

#### 数据结构建议

每个宠物形象包含：

- 唯一 ID 和显示名称。
- 图标、立绘或动画素材。
- 支持的动作列表。
- 默认人格配置。
- 点击反馈列表。
- 可用装扮槽位。

#### 当前数据驱动实现

- 每只普通宠物是 `assets/pets/<pet_id>` 下的自包含资源包。
- `pet.tres` 保存身份、排序、动作贴图、显示尺寸、点击轮廓、特效和基础动作参数。
- `PetRegistry` 启动时自动发现有效宠物包，不维护需要手工同步的硬编码宠物列表。
- `PetVisual` 是所有宠物共用的表现组件；点击、键盘或鼠标动作缺少专用贴图时回退到待机图。
- 右键菜单根据注册表动态生成宠物选项；存档只保存稳定的 `selected_pet_id`。
- 新增普通宠物不得要求修改 `main.gd` 或主场景。完整契约见 `docs/宠物资源包规范.md`。

#### 后续装扮

- 可考虑帽子、脸部、身体、手持物和背景特效等槽位。
- 首版先完成外观数据结构，不制作完整商店。
- 商店应优先使用通过游玩获得的游戏内资源；真实货币或 DLC 以后再决定。

#### AI 辅助美术生产

宠物形象、动作草图、皮肤与部分装扮可以由 Codex 的图像生成能力协助制作，但不能把“一次生成整套素材”视为可直接发布的最终流程。每个角色需要经过参考锁定、逐动作生成、透明背景处理和引擎内检查。

建议采用以下资产管线：

1. **美术规范**：先确定画风、轮廓比例、观察尺寸、线条、光照、调色板和禁止元素。
2. **角色提案**：为同一概念生成若干候选形象，只选择一个继续。
3. **标准母版**：制作正面、侧面、背面、表情和关键细节参考，作为后续所有动作的身份基准。
4. **动作清单**：逐个生成待机、点击、输入、专注、提醒、睡觉等动作，不在一个请求中混合大量不同资产。
5. **透明化与切帧**：先在纯色可移除背景上生成，再去除背景、切分帧并组装图集。
6. **一致性检查**：检查脸、身体比例、配色、标记、道具方向和大小是否跨动作漂移。
7. **引擎验收**：在实际桌面显示尺寸、不同 Windows 缩放和深浅背景上测试。
8. **单点修复**：只重做失败动作或单帧，避免每次重新生成整套角色。

首发建议先完成一个宠物的完整资产管线，再制作第二个宠物。这样可以先验证动作尺寸、透明边缘、播放节奏和 Godot 导入设置，避免多个角色同时返工。

AI 生成素材尤其需要注意：

- 小尺寸下的轮廓和表情可读性。
- 多动作之间的角色身份一致性。
- 毛发、半透明材质和软阴影的背景移除质量。
- 像素风可能需要人工像素级清理；手绘贴纸或简洁卡通风通常更适合快速原型。
- 装扮若需要自由组合，应从一开始按身体锚点和独立图层制作，不能只生成整张合成图。
- 所有角色应采用原创设计，不直接仿制 QQ 宠物、ChatGPT/Codex Pet 或其他受保护角色。

### 5.3 动作与动画系统

#### 基础动作

- 待机。
- 观察鼠标或四处张望。
- 坐下或趴下。
- 睡觉。
- 开心。
- 被点击后的回应。
- 专注陪伴动作。
- 提醒动作。

#### 动作切换规则

宠物同一时间只有一个主动作。动作来源按优先级覆盖：

1. 重要提醒。
2. 用户主动互动。
3. 专注计时状态。
4. 键盘与鼠标活动。
5. 时间或状态触发动作。
6. 普通待机与随机动画。

随机动画应设置冷却时间，避免宠物不停活动造成干扰。夜间可以增加睡觉概率，专注期间降低随机动作频率。

#### 可扩展状态

- 情绪：平静、开心、困倦、期待。
- 时间：白天、夜间。
- 用户状态：专注中、休息中、长时间无互动。
- 关系等级：陌生、熟悉、亲密。

第一版不建议制作饥饿、清洁、生病等带惩罚的生存数值，以免提醒助手变成负担。

### 5.4 点击互动

#### 首版互动

- 单击：播放一个短反馈，例如看向用户、开心、疑惑或发出气泡。
- 连续点击：宠物表现出不同反应，避免重复同一动画。
- 右键：打开快捷菜单。
- 拖动：移动宠物，而不是触发普通点击。

#### 后续互动提案

- 抚摸：按住并移动鼠标触发。
- 投喂或送礼。
- 宠物追逐鼠标指针。
- 将宠物拖到屏幕边缘后坐在边缘。
- 宠物偶尔主动发起一个微小互动，但必须有频率限制。

### 5.5 键盘与鼠标活动感应

#### 产品体验

用户在其他应用中敲击键盘或点击鼠标时，宠物会同步做出“敲打、打字、踩键盘或挥爪”等动作，让宠物看起来正在陪用户一起工作。

键盘和鼠标使用不同的动作标签：

- 键盘输入：敲键盘、打字、弹奏或连续拍打。
- 鼠标点击：单次拍击、戳一下或快速点按。
- 同时持续操作：进入通用的“忙碌工作”循环。
- 停止输入一段时间：自然结束动作并回到待机。

每个宠物可以为相同活动配置不同动作。例如猫用爪子拍键盘，机器人闪灯输入，史莱姆用身体弹跳。

#### 动画节流

不能为每一个系统输入事件完整播放一次动画，否则高速打字时动画会排队或闪烁。建议采用活动强度状态：

1. 第一次输入立即触发起手动作。
2. 最近约 300～500 毫秒内持续有输入时，保持循环动作。
3. 输入停止约 600～1000 毫秒后，播放收尾动作并回到待机。
4. 单次鼠标点击可播放很短的拍击反馈；连续点击合并为循环。
5. 提醒、用户直接点击宠物等高优先级动作仍可覆盖输入动作。

具体阈值在试玩中调整，并允许对动画敏感的用户关闭“跟随输入动作”。

#### 计数与展示

默认分开记录：

- 当前会话键盘敲击次数。
- 当前会话鼠标点击次数。
- 今日键盘敲击次数。
- 今日鼠标点击次数。
- 可选的历史累计与每日趋势。

建议在宠物详情或活动托盘中显示统计，不在桌面上持续显示大型数字。可以提供里程碑对白，例如“今天已经敲了很多下啦，要不要休息一下？”

原始敲击数不直接兑换货币或高价值奖励，避免玩家使用连点器或脚本刷取资源。若以后关联成长，只使用有每日上限的“活跃陪伴时间”或低价值里程碑。

#### 隐私边界

此功能必须明确区分于键盘记录器：

- 默认关闭全局活动感应，首次开启时解释用途并取得用户同意。
- 只统计“发生了一次键盘输入或鼠标点击”。
- 不保存具体按键、输入文本、快捷键组合、鼠标坐标或点击内容。
- 不记录用户正在使用的应用、窗口标题、网页或文件。
- 事件在内存中立即转成计数和活动强度，丢弃原始输入信息。
- 统计数据默认只保存在本地，不进入聊天 Prompt、分析服务或 Steam 云，除非用户明确选择。
- 提供托盘中的“暂停活动感应”和“一键清除统计”。
- 不要求管理员权限；在无法读取输入的高权限或受保护窗口中接受计数缺失。

#### 初步验收标准

- 游戏未获得焦点时，普通键盘和鼠标活动仍能触发宠物动作。
- 快速输入不会创建无限动画队列，也不会明显增加 CPU 占用。
- 键盘与鼠标计数可以独立开关和清除。
- 关闭感应后不再监听全局输入事件。
- 日界线、系统睡眠和游戏重启不会导致重复或负数统计。
- 日志和存档检查中不存在具体按键、文本或鼠标坐标。

### 5.6 番茄钟

#### 默认流程

1. 用户开始 25 分钟专注。
2. 宠物切换到安静的专注陪伴动作。
3. 专注结束时播放提醒动画和可选提示音。
4. 用户选择开始 5 分钟休息、延后或结束。
5. 完成若干专注时段后，可建议一次较长休息。

#### 可配置项

- 专注时长。
- 短休息和长休息时长。
- 长休息前的专注次数。
- 提示音和音量。
- 是否显示桌面通知。
- 是否自动开始下一阶段。
- 是否记录专注历史。

#### 失败与恢复

- 退出或崩溃后，计时器根据真实结束时间恢复，而不是从头开始。
- 电脑睡眠后，应根据用户设置选择“继续按真实时间计算”或“暂停”。
- 修改系统时钟时要避免重复奖励或异常提醒。

### 5.7 健康与日常提醒

#### 预设提醒

- 喝水。
- 站起来活动。
- 远眺或休息眼睛。
- 用户自定义提醒。

#### 提醒交互

每次提醒提供：

- 完成。
- 延后，例如 5、10 或 15 分钟。
- 跳过本次。
- 暂停今天的此类提醒。

#### 低打扰设计

- 提醒默认使用宠物动作、气泡和轻提示音，不强制弹出大型窗口。
- 支持勿扰时段。
- 专注阶段可以暂存非紧急提醒，在休息阶段统一提示。
- 对连续忽略的提醒降低频率，不使用责备性语言。

### 5.8 AI 宠物对话

#### 产品目标

让宠物以稳定、简短、有辨识度的口吻与用户对话，并在用户允许的情况下记住少量长期信息。对话应像桌面宠物，而不是把完整通用聊天机器人塞进游戏。

#### 重要可行性结论

- ChatGPT 订阅与 OpenAI API 是分开管理、分开计费的服务，不能默认通过用户的 ChatGPT Plus 或 Pro 订阅为游戏 API 调用付费。
- Claude.ai 的 Free、Pro、Max 等消费者套餐与 Anthropic API Console 同样是分开的产品；Claude 订阅不包含 Console API 用量。
- 截至 2026-07-19，没有适合独立 Windows/Steam 游戏的通用授权流程，可以让玩家登录 ChatGPT 或 Claude 消费者账号，并直接继承其聊天套餐的模型和消息额度。
- 因此不能实现“ChatGPT Free 玩家自动用免费模型、Plus/Pro 玩家自动用高级模型”这一精确方案。用户的聊天订阅等级与第三方游戏的 API 模型权限没有直接对应关系。
- 可以实现相近的 **BYOK（Bring Your Own Key，用户自带 API 密钥）** 方案：玩家连接自己的 OpenAI API Platform、Anthropic Console 或其他受支持 API 账户，调用费用由该 API 账户承担。
- BYOK 模式中可用的模型取决于用户 API 账户的模型权限、余额、地区和供应商限制，而不是 ChatGPT Plus/Pro 或 Claude Pro/Max 等聊天订阅等级。
- 开发者自己的 API 密钥不能放进公开发布的 Windows 客户端，否则可能被提取并滥用。
- 如果使用开发者统一提供的 AI 服务，推荐架构是：游戏客户端 → 自有后端 → OpenAI API。

#### 商业与认证方案

**方案 A：开发者提供 AI 服务，推荐作为正式产品方案**

- 游戏用户不需要理解 API 密钥。
- 开发者后端保存项目密钥并控制额度、速率和滥用。
- 可给每位玩家每日免费对话次数，未来再决定是否提供高级额度。
- 缺点是开发者承担服务器、API 成本和隐私责任。

**方案 B：用户自带 API 账户与密钥，适合高级设置或早期版本**

- 首期可支持 OpenAI API Platform 与 Anthropic Console，后续通过统一 Provider 接口加入其他模型服务或本地模型。
- 用户自己承担 API token 费用，并自行管理供应商账户余额、限额和可用模型。
- 设置流程应明确写成“连接 OpenAI API”或“连接 Anthropic API”，不能描述成“连接 ChatGPT/Claude 订阅”。
- 密钥只保存在当前 Windows 用户的系统凭据存储中，不写入普通存档、日志、崩溃报告、Steam 云存档或分析事件。
- 游戏不显示完整密钥，只显示连接状态、供应商、所选模型和可选的用量估算。
- 提供“测试连接”“立即断开”和“删除本地密钥”。
- 允许用户选择模型，也可以提供“经济 / 均衡 / 高质量”档位，将档位映射到该供应商当前允许用户调用的模型。
- 在发送前显示清晰的费用提醒，并提供每次回复的最大输出长度、每日软限制和用量统计。
- 桌面客户端中的用户密钥仍存在被本机恶意软件或逆向工具读取的风险；使用 Windows 凭据保护可以降低风险，但不能承诺绝对安全。
- OpenAI 官方安全建议不在客户端部署 API 密钥，因此 OpenAI BYOK 应标记为高级功能并提供充分风险说明；正式大众版本仍优先考虑短期授权能力或开发者后端。

**方案 C：首版不提供在线 AI**

- 使用预写对白和规则系统先验证宠物人格与互动节奏。
- 后续加入 AI，不阻塞核心桌面宠物发布。

当前建议：原型阶段采用方案 C 验证宠物人格，同时实现方案 B 的多供应商 BYOK 技术原型。首发可以把 BYOK 放在“实验性 / 高级设置”中，让普通玩家继续使用预写对白；是否增加方案 A，根据使用率、成本和安全测试决定。

#### 多供应商连接体验

设置页建议采用统一流程：

1. 用户选择 AI 供应商：OpenAI API、Anthropic API，后续可扩展其他供应商或本地模型。
2. 游戏显示该供应商 API 账户的开通链接和简短说明。
3. 用户输入 API 密钥，游戏测试连接并查询或验证可用模型。
4. 用户选择“经济 / 均衡 / 高质量”或具体模型。
5. 游戏显示“费用由你的 API 供应商账户收取”，并让用户确认。
6. 用户可以随时断开连接；断开后自动回到预写对白。

为了避免模型名称变更影响存档，游戏内部保存能力档位和供应商模型 ID，不把某个具体模型永久写死在宠物逻辑中。

#### 使用消费者订阅额度的官方路径

截至 2026-07-19，只有把 AI 体验放进模型供应商自己的产品环境，才可能正式使用玩家的消费者套餐额度：

**ChatGPT App 或自定义 GPT**

- ChatGPT Apps 按用户套餐的正常 ChatGPT 使用限制运行。
- 自定义 GPT 和 ChatGPT App 设计为在 ChatGPT 内使用，不能作为模型后端嵌入独立 Steam 游戏。
- 可以制作一个“宠物伴侣 ChatGPT App”，让玩家在 ChatGPT 内与同一人格对话，甚至通过开发者服务读取经过授权的部分宠物数据。
- 缺点是玩家需要离开桌面宠物窗口进入 ChatGPT，不能实现游戏内无缝聊天。

**Claude AI-powered Artifact**

- 玩家使用 Claude 账号登录后，Artifact 中的 AI 用量可以计入玩家自己的 Claude 使用限制，不需要开发者 API 密钥。
- Artifact 可发布并嵌入允许的网站，但其 AI 能力运行在 Anthropic 的 Artifact 环境中。
- 当前仅提供受限的文字生成能力，不支持完整 Anthropic API、外部 API 调用或持久化存储。
- 可以研究把网页 Artifact 作为独立伴侣页面，但不应把它当作 Steam 客户端内稳定、完整的对话后端。

**明确禁止的非官方做法**

- 不读取或复用用户浏览器中的 ChatGPT、Claude 登录 Cookie。
- 不通过网页抓取、自动化点击或未公开接口模拟官方客户端。
- 不调用 Claude Code、Codex 等官方客户端的内部登录令牌为游戏提供通用模型服务。
- 不要求玩家导出会话令牌或账号密码。

这些方法安全性差、容易失效，也可能违反供应商条款。

当前产品建议仍是：桌面游戏使用离线对白加可选 BYOK；如果希望验证“订阅额度对话”，可以额外制作一个 ChatGPT App 或 Claude Artifact 概念版本，但将其视为伴侣入口，而不是 Steam 游戏的底层模型服务。

#### 宠物人格提示词

提示词至少包含：

- 宠物身份、性格、口头习惯和世界观。
- 回答长度限制，默认 1～3 句。
- 当前动作、情绪、关系等级和提醒上下文。
- 已确认的长期记忆摘要。
- 禁止冒充医生、心理治疗师或真人。
- 不编造自己做过真实世界中的动作。
- 当用户表达紧急危险或高风险问题时，不继续角色扮演误导用户。

不同形象可以使用不同人格配置，但底层安全和隐私规则共用。

#### 对话记忆设计

“打开记忆”不能只依赖模型上下文，应由游戏明确管理：

1. **最近对话**：保留最近若干轮，用于自然承接当前话题。
2. **短期摘要**：定期把较长对话压缩成摘要，控制调用成本。
3. **长期记忆**：只保存适合长期使用的事实，例如称呼、偏好、长期目标和宠物共同经历。
4. **临时内容**：默认不进入长期记忆。

用户必须能够：

- 关闭长期记忆。
- 查看宠物记住了什么。
- 删除单条记忆。
- 清除全部聊天和记忆。
- 选择聊天记录仅本地保存或不保存。

#### 初步 AI 验收标准

- 宠物口吻在多轮对话中保持稳定。
- 用户追问时，宠物能理解最近上下文。
- 重启游戏后，只恢复用户允许保存的记忆。
- 没有网络或额度不足时，宠物仍能使用预写对白作出反馈。
- API 错误不会导致游戏卡死或宠物消失。

### 5.9 关系与轻量养成

这是 P2 提案，目的是增强陪伴感，而不是制造压力。

- 完成专注、响应健康提醒、与宠物互动可增加陪伴经验。
- 关系升级可以解锁动作、对白或外观，不降低等级。
- 不因用户数天未登录而惩罚、掉好感或让宠物生病。
- 每日奖励应轻量，避免强迫登录。

### 5.10 本地存档

存档至少包含：

- 当前宠物和外观。
- 窗口位置、缩放和置顶状态。
- 番茄钟与提醒设置。
- 活动感应开关，以及用户选择保留的键盘与鼠标聚合计数。
- 专注历史和关系进度。
- 对话设置、用户允许保存的记忆。
- 数据版本号，用于后续升级存档格式。

建议保留一个主存档和若干自动备份。AI 聊天记录和普通游戏进度应分开存储，便于用户独立删除隐私数据。

## 6. 非功能需求

### 性能

- 空闲时保持低 CPU 占用。
- 动画帧率可配置或在后台自动降低。
- 高频输入事件必须合并处理，不能为每次敲击分配长期对象或排队完整动画。
- 内存占用应适合长时间常驻。

### 隐私与安全

- 明确说明哪些数据保存在本地、哪些内容会发送到 AI 服务。
- 默认不采集聊天内容用于分析。
- 全局输入感应只保存聚合计数，不保存按键、文本、鼠标位置、窗口或应用信息。
- 不把开发者 API 密钥或其他服务密钥写入客户端。
- 所有聊天历史和长期记忆必须可删除。

### 可访问性

- 提醒不能只依赖声音，同时提供动画或文字。
- 可关闭闪烁、抖动和突然放大的动画。
- 读取并尊重 Windows 的减少动画设置；开启时使用静态帧或更轻微的待机效果。
- 支持 UI 缩放和清晰字体。
- 主要功能可通过托盘菜单访问。

## 7. 技术模块草案

建议将系统拆成以下独立模块：

- `DesktopWindowManager`：透明窗口、置顶、多显示器和位置恢复。
- `PetStateMachine`：动作优先级、状态切换和随机动作。
- `PetAppearanceManager`：宠物形象、动画资源和装扮。
- `InteractionManager`：点击、拖动、抚摸和快捷菜单。
- `InputActivityMonitor`：接收 Windows 全局键盘与鼠标活动，立即转换为匿名计数和活动强度，并负责启停监听。
- `ActivityStats`：管理会话、今日和历史聚合统计，不接触原始输入内容。
- `TimerManager`：番茄钟和真实时间恢复。
- `ReminderManager`：健康提醒、延后和勿扰。
- `ActivityQueue`：统一管理计时完成、需要用户处理的提醒和未读事件，并按优先级显示。
- `SaveManager`：版本化存档和备份。
- `DialogueManager`：预写对白、AI 服务降级和界面。
- `MemoryManager`：最近对话、摘要和长期记忆。
- `AIProvider`：统一 OpenAI、Anthropic 和未来供应商的连接、模型能力、错误与用量信息，避免游戏逻辑绑定单一模型。
- `CredentialStore`：使用 Windows 系统凭据能力保存用户自带密钥，并确保密钥不进入存档、日志和 Steam 云。
- `SteamAdapter`：后期接入成就和云存档。

## 8. 第一版建议范围

### 原型 0.1：桌面生命感

- 一个占位宠物形象。
- 透明窗口、拖动和始终置顶。
- 待机、随机动作和点击反馈。
- 本地保存位置和设置。

### 原型 0.2：实用陪伴

- 番茄钟。
- 喝水和站立提醒。
- 键盘与鼠标活动触发动作，以及本地聚合计数。
- 专注、提醒和休息动作。
- 托盘菜单和勿扰设置。

### 原型 0.3：人格验证

- 预写对白系统。
- 一个稳定的宠物人格。
- AI 对话独立技术验证。
- 最近对话和少量可管理的长期记忆原型。

### 首发候选版

- 至少两个宠物形象。
- 完整设置和自动备份。
- 经过测试的提醒体验。
- 基础关系成长。
- 是否包含在线 AI，根据成本、隐私和稳定性测试决定。
- 最后接入 Steam 上传、成就和云存档。

## 9. 暂不进入首版的功能

- 多人互动和访问好友宠物。
- 宠物繁殖。
- 大型地图或房间装修。
- 复杂经济系统。
- 真实货币微交易。
- Steam 创意工坊。
- 宠物之间的自动 AI 对话。
- 摄像头或麦克风常驻监听。

## 10. 参考产品分析：ChatGPT / Codex Pets

### 10.1 产品定位

ChatGPT/Codex Pets 是可选的动画伙伴，主要用途是让用户在离开主窗口时仍能观察 AI 工作状态。选择不同宠物只改变外观，不改变 ChatGPT 或 Codex 完成任务的方式。

它本质上是“拟人化任务状态指示器”，而不是完整的虚拟宠物游戏。

### 10.2 已确认功能

- 桌面应用提供可移动的悬浮宠物覆盖层。
- 可以通过设置、命令菜单或 `/pet` 唤醒和收起宠物。
- 宠物选择和桌面位置会在重新打开应用后保留。
- 支持内置宠物与本地自定义宠物。
- 点击宠物可返回 ChatGPT；点击活动可打开对应的聊天任务。
- 多个聊天同时工作时，活动托盘集中显示状态。
- 状态包括：
  - `Running`：任务正在执行。
  - `Needs input`：需要用户批准、回答或作出决定。
  - `Ready`：任务已完成，但用户尚未查看。
  - `Blocked`：任务失败或出现系统错误。
- 多任务状态优先级为：需要输入 → 失败阻塞 → 已完成 → 正在运行。
- macOS 上 Computer Use 画中画窗口可以附着在宠物旁边。
- 尊重操作系统的“减少动画”设置，开启后显示静态帧。
- 网页版宠物只出现在支持的 Work 模式聊天中，没有桌面悬浮覆盖层或活动托盘。

### 10.3 自定义宠物系统

- 用户可以描述希望创建的宠物，由 `hatch-pet` 技能生成形象和动作素材。
- 自定义宠物保存在本机，不自动同步到 ChatGPT 网页版。
- 可上传透明 PNG 或 WebP 精灵图；当前官方格式要求为 `1536 × 1872`、不超过 20 MiB。
- 官方生成工作流采用 `8 × 9` 图集、每格 `192 × 208`。
- 当前动画契约包含九种状态：
  - `idle`
  - `running-right`
  - `running-left`
  - `waving`
  - `jumping`
  - `failed`
  - `waiting`
  - `running`
  - `review`
- 官方生成流程允许像素、毛绒、黏土、贴纸、矢量、3D 玩具和绘画等风格，但要求小尺寸轮廓清楚、跨动作形象一致。

### 10.4 与本项目逐项比较

| 维度 | ChatGPT / Codex Pet | 本项目设想 |
|---|---|---|
| 核心目的 | 展示 AI 后台任务状态 | 桌面陪伴、专注与健康提醒、轻养成 |
| 悬浮窗口 | 有；位置可保存 | 有；另需可靠的置顶开关、多显示器和缩放 |
| 状态动画 | 与任务运行、待确认、完成、失败绑定 | 与待机、时间、专注、休息、提醒、情绪和互动绑定 |
| 点击行为 | 返回 ChatGPT 或打开相关任务 | 抚摸、反馈、聊天、菜单及相关提醒 |
| 外观 | 内置或本地自定义，可 AI 生成 | 多角色、皮肤、装扮和后期商店 |
| 人格 | 宠物主要是视觉外观，不改变 AI 行为 | 每只宠物可有稳定人格、口吻和关系表现 |
| 宠物对话 | 没有独立的宠物人格对话系统 | 预写对白加可选 AI 对话 |
| 长期记忆 | 没有宠物专属长期记忆 | 用户可管理的本地长期记忆 |
| 提醒 | 工作状态与系统通知 | 番茄钟、喝水、活动、眼睛休息和自定义提醒 |
| 输入响应 | 不以普通键鼠活动作为宠物核心输入 | 键盘敲击和鼠标点击驱动陪伴动作与本地计数 |
| 活动列表 | 多聊天活动托盘 | 可发展为计时器和待处理提醒托盘 |
| 养成 | 无 | 关系等级、解锁动作与外观 |
| 离线体验 | 依赖 ChatGPT/Codex 工作状态 | 核心宠物、计时和预写对白离线可用 |
| 商业模式 | ChatGPT/Codex 产品体验的一部分 | Steam 买断为主，后续外观内容待定 |

### 10.5 值得借鉴的设计

1. **统一活动状态**：把“专注中、提醒待处理、计时完成、出错”统一为明确状态，并用固定优先级决定宠物动作。
2. **活动托盘**：点击宠物旁的小托盘，可查看番茄钟、被延后的喝水提醒和未完成事项。
3. **唤醒与收起**：提供非常快速的显示/隐藏入口，并记住宠物位置。
4. **外观与逻辑分离**：换宠物不应破坏计时、提醒和存档；人格是否跟随外观由单独配置决定。
5. **数据驱动动画**：从第一版就让动画帧数、速度、循环方式和触发事件写在角色配置中，避免硬编码。
6. **减少动画**：跟随系统设置，并提供游戏内独立开关。
7. **自定义素材契约**：以后若开放玩家宠物或 AI 生成宠物，应先定义统一图集、动作名称、尺寸和自动验证工具。

### 10.6 我们应保持的差异化

- 宠物在没有 AI 任务时仍然有生命感，而不是只充当状态灯。
- 提醒功能与宠物情绪和动作结合，但不责备或惩罚用户。
- 对话人格、记忆和关系成长属于宠物本身。
- 核心体验不依赖云端 AI，也不依赖持续订阅。
- 动作系统允许每个宠物扩展特色动作，而不是所有宠物只能使用固定九种动画。

### 10.7 已观察到的实现风险

OpenAI 官方 GitHub 仓库中的用户报告暴露了几个值得提前规避的问题：

- Windows 11 上悬浮宠物可能失去始终置顶状态。
- 靠近屏幕边缘时，宠物或活动托盘可能被覆盖层窗口边界裁切。
- 固定缩放和强制像素化会让非像素美术产生锯齿。
- 固定图集和硬编码动作序列限制了自定义宠物的表现力。
- AI 生成完整多动作宠物可能耗时、消耗额度，并出现跨动作形象漂移或生成失败。

这些是公开问题报告，不代表所有用户都会遇到，但应转化为本项目的早期测试项。

## 11. 市场竞品研究：桌面宠物与桌面放置游戏

> 调研日期：2026-07-19。评价数量与好评率会随时间变化；它们能说明产品整体接受度，但不能单独证明某一个功能造成了成功。

### 11.1 市场上已经验证的几种路线

| 产品 | 市场信号 | 主要体验 | 对本项目的启发 |

### 11.2 我们已有但可以加强的功能

#### 键鼠动作：从“会响应”发展为“有温和的结果”

Bongo Cat 的成功是对本项目键鼠感应方向的强验证。我们已经规划了输入动画和分项计数，尚缺的是反馈闭环：

1. 用户工作或完成专注；
2. 宠物同步做动作；
3. 活动积累为有限的“陪伴进度”；
4. 宠物偶尔带回贴纸、小摆件、回忆卡或装扮；
5. 收藏品进入图鉴，用户可以收藏常用外观。

不建议照搬“每次按键直接产币”。更安全的方案是将原始计数与游戏进度分开：按固定时间窗口合并活动事件、设置每日软上限，并优先奖励完成专注时段。这样既避免鼓励无意义刷按键，也降低自动化作弊和隐私误解。

#### 专注提醒：从计时器发展为“陪伴工作模式”

现有番茄钟可以补充一个真正的专注模式：

- 降低随机动画和气泡频率；
- 隐藏不必要的计数、商店入口和成长提示；
- 宠物切换为读书、敲键盘、整理物品或安静趴睡；
- 支持屏幕底部条、侧边条、自由悬浮和第二显示器布局；
- 专注结束后再集中结算进度和展示奖励。

这比单纯多做一个计时器更符合本项目的定位。

### 11.4 建议暂缓或明确避开的设计

- **可交易随机物品和 Steam 市场经济**：会引入刷取、机器人、定价、欺诈和地区法规问题。
- **付费抽卡、极低概率稀有掉落和无保底机制**：容易破坏治愈感，也会让输入统计变成刷取压力。
- **深度繁育、进化、战斗和大型探索**：它们都能成为好游戏，但会改变当前产品的核心类型。
- **默认干扰鼠标或移动窗口的恶作剧**：可以成为明确选择加入的“淘气模式”，不能成为默认行为。
- **依赖知名授权角色和大量 DLC**：授权、分成和内容产能风险高；首版应建立原创宠物辨识度。
- **把待办、日记和习惯追踪做成完整效率套件**：这些工具应服务宠物体验，不能让产品失去轻量性。

### 11.5 对当前路线的初步建议

首版原型不需要因为竞品调研而明显扩张。建议保留当前 P0/P1，并只新增两个设计要求：

1. **纯陪伴 / 低打扰模式**：从架构和设置层面尽早支持。
2. **为未来收藏闭环留接口**：键鼠活动和专注完成只发出统一事件，首版可以只统计，后续再让事件产生收藏进度。

如果原型证明宠物本身足够可爱，再按以下顺序扩展：

`收藏图鉴与小纪念物 → 简单今日待办 → 桌面小空间与被动活动 → 环境音 → 双宠互动 → 小游戏或社交`

## 12. 开发启动判断与首个技术原型

### 12.1 启动结论

现有需求已经足够开始开发，不需要先完成全部角色设计、AI 方案、经济系统或 Steam 接入。此时继续增加功能的收益低于尽快验证桌面窗口体验。

首个原型的目标不是“做出完整游戏”，而是回答四个问题：

1. 透明宠物窗口在常见 Windows 设备上是否稳定、清晰且不挡操作？
2. 宠物能否可靠拖动、置顶、缩放并恢复位置？
3. 全局键鼠活动能否在不记录具体输入内容的前提下触发流畅动画？
4. 宠物仅凭待机、响应和偶发动作，是否已经产生陪伴感？

### 12.2 建议技术基线

- **引擎**：Godot 4.x 稳定版。
- **原型表现层**：先使用 GDScript，减少本地工具链依赖，尽快验证透明窗口、拖动、置顶、缩放和宠物动作。
- **Windows 集成层**：全局活动监听单独封装；在 GDExtension 原生模块与 Godot .NET/C# 方案完成小型技术对比后再确定，不让窗口和动画层直接依赖具体实现。
- **首发架构**：游戏表现层与 Windows 集成层分离；输入监听通过统一活动事件传给宠物，不让动画代码直接依赖系统钩子。
- **存档**：本地 JSON 或 Godot 配置文件，先保存窗口、显示和隐私设置。
- **美术**：首个原型使用占位宠物；角色风格确定后替换，不阻塞窗口和交互验证。
- **Steam**：保留平台接口层，开发期默认使用本地实现；发布前再接成就、云存档和 Steamworks。

Godot 官方支持透明、无边框、始终置顶、无焦点和鼠标穿透窗口，也支持用多边形限定宠物可点击区域。官方同时提示 Windows 混合显卡设备可能出现透明窗口问题，因此必须在早期测试不同渲染器。[Godot 桌面覆盖层文档](https://docs.godotengine.org/en/stable/tutorials/ui/creating_applications.html)

### 12.3 原型 0.1 的冻结范围

原型拆成两个连续的小里程碑。**0.1A 桌面外壳**只实现以下内容：

- 一个透明无边框的宠物窗口；
- 使用占位宠物显示待机动画；
- 鼠标拖动与位置恢复；
- 始终置顶开关；
- 75%、100%、125% 和 150% 显示比例；
- 鼠标只在宠物轮廓内被窗口接收，其他透明区域穿透；
- 键盘活动与鼠标活动的动作预览入口；
- 一个偶发动作；
- 退出后恢复窗口设置。

**0.1B Windows 活动桥接**随后加入：

- 全局键盘活动触发敲击动画；
- 全局鼠标点击活动触发拍打动画；
- 当前会话的键盘和鼠标聚合计数；
- 暂停活动监听与清除计数；
- 不解析、不记录具体按键、文本、坐标、应用或窗口信息。

本原型明确不做：

- 番茄钟和健康提醒；
- AI 对话；
- 好感度、货币、掉落和收藏；
- 商店、装扮和多宠物；
- 环境音和待办事项；
- Steam SDK、成就和云存档；
- 正式宠物美术。

### 12.4 原型验收门槛

- 在 Windows 11 的 100%、125%、150% 和 200% 缩放下，宠物位置和点击区域基本正确。
- 连接或断开第二显示器后，宠物不会永久留在屏幕外。
- 关闭置顶后能被普通窗口覆盖；开启后能恢复置顶。
- 透明区域不会阻挡下层窗口操作。
- 连续快速输入不会建立无限动画队列。
- 活动监听不保存按键值、输入文本、鼠标坐标、当前应用或窗口标题。
- 连续运行 30 分钟没有明显内存增长或异常 CPU 占用。
- 监听关闭后不再接收全局活动事件。

### 12.5 尚未决定但不阻塞开工的事项

- 正式视觉风格和第一只宠物；
- 宠物的名字、性格和对话语气；
- AI 是否进入首发以及具体供应商；
- 游戏价格与外观商业模式；
- 收藏、货币和养成深度；
- 环境音、多人、双宠和小游戏；
- Steam 商店页面、成就和云存档。

这些事项都可以在原型使用占位资产和抽象接口的情况下延后决定。

### 12.6 粗略时间预估

以下按单人开发、需求没有明显扩张估算：

| 阶段 | 全职开发 | 业余开发 |
|---|---:|---:|
| 可运行的技术原型 0.1 | 3–7 个工作日 | 1–3 周 |
| 包含提醒和基础设置的内部可玩版 | 3–6 周 | 2–3 个月 |
| 包含正式宠物、基础养成和可测试 AI 对话的首发候选版 | 2–4 个月 | 4–8 个月 |
| Steam 上架准备、测试、素材和审核缓冲 | 额外 2–4 周 | 额外 1–2 个月 |

最大的时间变量通常不是窗口代码，而是角色动画数量、一致性返修、AI 产品化、安全测试和范围扩张。

## 13. 风险与待验证事项

| 风险 | 影响 | 初步处理 |
|---|---|---|
| 透明置顶窗口挡住正常操作 | 高 | 提供置顶开关、缩放、隐藏和后续鼠标穿透 |
| 动画持续运行导致资源占用 | 高 | 降低空闲帧率，尽早进行长时间性能测试 |
| 全局输入感应被误解为键盘记录 | 高 | 默认关闭、明确授权、只保留聚合计数、公开隐私说明并检查日志 |
| 高频输入造成动画或事件队列堆积 | 高 | 事件合并、状态循环、冷却时间和长时间压力测试 |
| 提醒过于频繁 | 高 | 默认克制、允许延后、勿扰和按日暂停 |
| AI 调用费用不可控 | 高 | 后端限额、短回复、摘要记忆和预写对白降级 |
| API 密钥从客户端泄露 | 高 | 正式版通过后端代理，不嵌入开发者密钥 |
| 长期记忆侵犯隐私 | 高 | 明示同意、可查看、可逐条删除、默认保守保存 |
| 宠物人格不稳定 | 中 | 固定人格配置、限制回答长度、建立对话测试集 |
| 内容量不足 | 中 | 优先制作可复用动作规则和随机组合，而非大量一次性内容 |

## 14. 当前待决问题

以下问题会明显影响美术、交互和开发范围，建议接下来逐项确定：

1. **视觉风格**：像素风、手绘 2D、Live2D 感，还是简洁矢量风？
2. **宠物主题**：现实动物、幻想生物、机器人，还是允许多种主题共存？
3. **桌面位置**：自由悬浮，还是主要站在任务栏、窗口或屏幕边缘？
4. **互动气质**：治愈安静、活泼搞怪，还是略带毒舌？
5. **提醒方式**：只由宠物气泡提醒，还是同时使用 Windows 系统通知？
6. **番茄钟定位**：轻量附属功能，还是游戏成长的主要来源？
7. **AI 首发范围**：首发必须包含，还是先作为实验功能？
8. **AI 费用模式**：开发者承担有限额度、付费高级功能，还是暂时不联网？
9. **记忆范围**：只记偏好和称呼，还是也记工作目标、日程与情绪记录？
10. **养成深度**：只有关系等级和解锁，还是加入货币、任务与每日目标？
11. **宠物数量**：首发是多个可切换角色，还是一个角色的多套外观？
12. **目标价格**：免费、低价买断，还是买断加外观 DLC？
13. **活动统计保留**：只显示当前会话与今日次数，还是保留每日历史和趋势图？
14. **奖励闭环**：专注和活动是否解锁收藏物，还是始终只做统计？
15. **纯陪伴模式**：是否允许彻底关闭货币、等级、连续签到和掉落？
16. **桌面小空间**：宠物是否拥有可装饰的小窝、桌面或小岛？
17. **声音定位**：是否加入环境音混音器，还是保持游戏基本静音？
18. **布局模式**：除自由悬浮外，是否首发支持屏幕底部、侧边和第二显示器模式？

## 15. 当前已确认的决定

- 产品是类似 QQ 宠物的 Windows 桌面放置游戏。
- 第一只正式方向的宠物是原创巴哥犬 **Leo**；先以单张透明母版进行占位动画验证，之后再扩展一致的动作图集。
- 第二只宠物是以用户提供的真实长毛猫照片为原型创作的 **Bobo**，保留银金奶油色长毛、大绿眼和蓬松侧尾等辨识特征。
- 宠物形象采用自动发现的数据驱动资源包；新增普通宠物不修改核心代码。
- 游戏本体先独立完成，Steam 发布相关工作放到开发后期。
- 宠物可以切换不同形象。
- 支持番茄钟、喝水和站立活动等提醒。
- 支持始终置顶，并允许用户关闭。
- 宠物有多个动作和偶发动画。
- 点击宠物可以互动。
- 用户敲击键盘或点击鼠标时，宠物可以做出对应动作，并分别统计聚合次数。
- 宠物形象和动作素材可以由 Codex 图像生成能力协助制作，并通过统一美术规范与人工验收保持一致。
- 后期考虑通过游戏商店获得外观装扮，但优先级不高。
- 希望加入由 OpenAI API 驱动、带固定宠物人格和对话记忆的聊天功能。
- AI 对话希望支持多个模型供应商，并优先研究由用户自己的 API 账户承担 token 费用的 BYOK 模式。
